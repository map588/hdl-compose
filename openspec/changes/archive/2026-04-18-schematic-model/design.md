## Context

Parser layer exists: `parse_file(path) -> Result<Vec<ModuleDef>, ParseError>` with VHDL and Verilog support, bundle detection, and 23 passing tests. Current types (`ModuleDef`, `PortDef`, `GenericDef`, `PortType`, `Direction`) describe parsed module headers. No design-level model exists yet.

The tool's core thesis: text and canvas are two live views of one in-memory model. That model is `Schematic`. Everything else — GUI, project files, codegen — is a projection of it.

## Goals / Non-Goals

**Goals:**
- Define `Schematic`, `Instance`, `NetRef` types that represent a structural design.
- Implement net resolution: given a `NetRef`, resolve it to a concrete type/width for validation.
- Validate a schematic: catch direction mismatches, width mismatches, missing references, duplicate names.
- Serialize/deserialize `.hdlc` project files. `ModuleDef` is never stored — re-derived from source.
- Generate deterministic structural VHDL from a `Schematic`.
- Generate deterministic structural SystemVerilog from a `Schematic`.
- Upgrade error types to `thiserror`.

**Non-Goals:**
- GUI or canvas rendering.
- Mini editor or autocomplete logic.
- File watching or automatic re-parse on source changes.
- Hierarchical schematics (sub-designs within instances).
- Mixed-language projects (each project is one language).
- Behavioral code generation (processes, always blocks).

## Decisions

### 1. Net identity is the driver

Every net is identified by its source: `InstancePort(instance_name, port_name)` for internally-driven nets, or `TopPort(port_name)` for top-level ports. Multiple instance input ports can reference the same driver. No separate "signal declaration" concept in the model — signals in the generated HDL are derived from net drivers.

**Rationale:** This is the core insight from the design conversation. In a purely structural architecture, every net has exactly one driver by construction. Making the driver canonical eliminates a whole class of "orphan signal" bugs and makes the model simpler.

**Alternative considered:** Explicit signal declarations in the model (closer to raw VHDL). Rejected because it adds ceremony without value — the tool's job is to hide signal-declaration bookkeeping.

### 2. Aliases are optional display names, not identities

`Schematic.aliases: HashMap<NetId, String>` maps a net's canonical driver-based identity to a user-chosen name. Aliases affect generated signal names only. They don't change connectivity or identity.

**Rationale:** Users want `sys_clk` in the generated VHDL, not `pll_main_clk_out`. But the model's internal logic should always reason about nets via their driver.

### 3. Per-project language, stored in project file

`Schematic.language: Language` is `Vhdl` or `SystemVerilog`. Set once at project creation. Codegen dispatches on it. All library paths in the project must be the same language.

**Rationale:** User stated "each project is strictly the same language." Simplifies codegen and avoids mixed-language wrapper complexity entirely.

### 4. Project file stores connections, not ModuleDefs

The `.hdlc` file stores: top-level info, instances (with generic/port maps), aliases, library paths. It does NOT store parsed `ModuleDef` data. On load, library paths are re-parsed to rebuild the module library. Instances reference modules by name.

**Rationale:** Source files are the truth for module definitions. Storing parsed data would create a staleness/divergence problem. Re-parse on load is how dirty-detection stays honest.

### 5. Codegen output structure

One output file per schematic. Architecture/module named `structural`. Instance statements in alphabetical order by instance name. Signal names derived from driver unless aliased. Header comment: `-- Generated by hdl-compose. Edit the source .hdlc project file, not this file.`

**Rationale:** Deterministic output means `git diff` is meaningful. Alphabetical ordering prevents spurious diffs from reordering. Readable output means users can verify correctness without the tool.

### 6. Validation as a separate pass, not enforced at mutation time

`schematic.validate(&library) -> Vec<Diagnostic>` returns all issues. The model allows invalid states (unconnected ports, width mismatches) because a design-in-progress is always temporarily invalid. Codegen refuses to emit if validation has errors.

**Rationale:** Enforcing validity on every mutation would make the editor unusable — you can't type half a connection. Validate-before-codegen is the right boundary.

## Risks / Trade-offs

- **[Re-parse on load could be slow for large libraries]** → Acceptable for v1. Parser is fast (23 tests run in 0.04s). Can add caching by source_hash later if needed.
- **[No undo/redo in the model]** → Explicitly out of scope for v1. The model is mutable and doesn't track history. Undo is a GUI concern layered on top later.
- **[Alias collisions]** → Two different nets could be aliased to the same name. Validation catches this and reports an error.
- **[Generic expressions not evaluated]** → Generic map values stored as strings (e.g., `"1024"`, `"WIDTH*2"`). No expression evaluation — just pass through to codegen. The synthesizer handles evaluation.
